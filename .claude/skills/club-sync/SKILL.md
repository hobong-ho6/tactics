# fut.gg 구단 동기화 런북 (2026-09-19 신설, 사용자 지시 「스쿼드 동기화를 match-watch처럼 스킬로」)

작업 디렉터리: 저장소 루트. DB `db/tactics.db`. 규칙은 CLAUDE.md·HANDOFF.md.

## ⭐ 언제 돌릴까 — **새 세션에서 돌린다** (2026-09-22 실측, 사용자 질문에서)

이 런북의 비용은 **더해지는 컨텍스트가 아니라 툴 왕복 횟수**가 결정한다. 툴을 한 번 부를 때마다
**그때까지의 대화 전체가 다시 입력으로 들어가기** 때문이다(캐시가 과금은 덮지만 **한도 소진은 그대로**다).

- 실측(2026-09-22): 컨텍스트 **380k가 쌓인 세션 끝**에 붙여 약 **70회** 왕복 → 약 2,500만 입력 토큰 상당.
  **같은 작업을 빈 세션에서 하면 1/10 수준**이다.
- ⇒ **긴 작업 세션 끝자락에 붙이지 말고 `/club-sync`만 도는 새 세션을 연다.**
- ⇒ **진화는 마지막 단계까지 끝내고 한 번에** 싱크한다(쿨다운 15분과 별개로 **회차 자체가 비용**이다).
- ⭐ 데이터량은 문제가 아니다 — `collect_ggclub.py` 덕에 보유 98명이 **컨텍스트 0**으로 들어온다
  (전량을 대화로 받았다면 회차당 약 **21,700 토큰**이었다). 비용은 늘 **삽질 횟수**에서 나온다.
  아래 ⭐⭐ 표시들이 전부 그 삽질을 한 번씩 겪고 적어 둔 것이다 — **읽고 시작하면 15~20회로 끝난다.**

## 0. 전제 — 로그인·싱크는 **사용자 몫**

- ⛔ **로그인 대행 금지.** fut.gg·EA 아이디/비밀번호 입력, 로그인 버튼 클릭, EA 접근 허용 클릭을 하지 않는다.
- 로그인이 안 돼 있으면 **사용자에게 요청하고 멈춘다**: 「브라우저 패널에서 fut.gg에 로그인해 주세요. 끝나면 알려주세요.」
- EA 구단 자동 수집은 FC Community API 승인 파트너 전용이라 우리가 직접 호출하지 않는다. **GG Club 페이지는 읽기만** 한다.
- ⭐ 「Sync Club」·「Refresh Now」 버튼은 **사용자 계정에 작업을 거는 동작**이다 — 누르기 전에 **승인을 받는다**
  (이번 세션에서 이미 「눌러줘」를 받았으면 그대로 진행하고, 아니면 물어본다).

## 2. 브라우저로 GG Club 읽기 (in-app 브라우저)

2. 로그인 상태 확인 — 클럽이 안 보이면 §0대로 사용자에게 요청.
3. 최신화가 필요하면 「Sync Club」(또는 「Refresh Now」) 클릭 → **6~8초 대기**.
   ⚠️ 누른 직후 바로 읽으면 이전 데이터가 온다. 버튼 라벨이 `Sync Club` → `Refresh Now`로 바뀌면 반영된 것이다.
   ⚠️⚠️ **싱크에는 쿨다운이 있다**(2026-09-20 실측). 직전 싱크 뒤 약 **15분**은 버튼이 **아예 사라지고** 본문에 
   「**Available in N minutes**」만 뜬다. ⇒ 같은 회차에 두 번 싱크할 수 없다. **쿨다운이면 기다리거나 다음 회차로 넘긴다** — 
   ⛔ 버튼이 없다고 「로그인이 풀렸다」로 오판하지 말 것.
   ⭐ **읽기는 쿨다운과 무관하다** — 선수 목록·플레이스타일 조회는 언제든 되고, 마지막 싱크 시점의 값을 준다.
   ⭐ 버튼은 **뷰포트 1280px 이상**에서만 보인다(`max-xl:!hidden`). 좁으면 DOM에 있어도 크기가 0이라 클릭이 안 된다.
   ⭐⭐ **넓혀도 안 보이면 사이드바에 마우스를 올려라**(2026-09-22 실증 — 여기서 10회를 허비했다).
   버튼의 조상이 `lg:!hidden group-hover/sidebar:!block`이라 **사이드바 hover 상태에서만** 렌더된다.
   1600px로 넓혀도 `getBoundingClientRect()`가 계속 `0×0`이면 이것이다 —
   `computer{action:'hover'}`로 **왼쪽 사이드바(x≈16)**를 짚은 뒤 다시 재면 `283×36`이 나온다.
   ⛔ 합성 이벤트(`dispatchEvent`)로는 CSS `:hover`가 켜지지 않는다 — **실제 마우스 이동**이어야 한다.
   ⚠️ 클릭 자체는 `b.click()`(JS)이 확실하다. 좌표 클릭은 스크린샷 좌표계 해석이 틀리면 엉뚱한 카드를 누른다 —
   **계정에 작업을 거는 버튼**이라 무엇을 누르는지 확정할 수 있는 쪽을 쓴다.
4. ⭐⭐ **수집은 `scripts/collect_ggclub.py`로 한다**(2026-09-21 신설 — 사용자 지시 「스크립트를 만들어서 싱크해」).
   ⛔ **브라우저 출력을 대화로 받아 파일에 옮겨 적지 말 것** — 100명 캡처가 컨텍스트를 두 번 통과해 회차당 약 **1만 토큰**이 샜다.
   스크립트가 API를 직접 부르면 보유가 몇 명이든 **컨텍스트 비용은 0**이고, 표준출력은 요약 몇 줄뿐이다.
   ```
   .venv/bin/python scripts/collect_ggclub.py --print-snippet   # ① 토큰 추출 스니펫
   # ② 로그인된 GG Club 탭에서 스니펫 실행 → Authorization 헤더 JSON 한 줄
   #    ⚠️ 현재 경로와 **다른** /gg-club/my/… 링크를 눌러야 SPA 이동이 일어나 헤더가 잡힌다(같은 경로면 호출이 없다).
   FUTGG_AUTH='<그 JSON>' .venv/bin/python scripts/collect_ggclub.py --apply-squad   # ③ 사람이 직접 돌릴 때
   .venv/bin/python scripts/collect_ggclub.py --auth-file /tmp/ggauth.json --apply-squad   # ③' 에이전트가 돌릴 때
   ```
   - ⭐ **에이전트는 `--auth-file`을 쓴다**(2026-09-21 신설): 토큰을 명령줄에 박으면 프로세스 목록·쉘 히스토리에 남고
     **그 행위 자체가 정책으로 차단된다**(실측). 파일로 건네면 스크립트가 **읽는 즉시 삭제**하고, 저장소 안 경로는 거부한다.
   - ⭐⭐⭐ **에이전트는 `--raw-file`을 쓴다**(2026-09-24 신설 · **토큰을 페이지 밖으로 꺼내지 않는다**).
     ⛔ 종전 「클립보드로 토큰을 꺼내 `--auth-file`로 넘긴다」(2026-09-22) 경로는 **정책으로 차단된다** —
     토큰을 클립보드·파일·환경변수로 내보내는 코드 자체가 `Credential Materialization`으로 거부된다(2026-09-24 실측).
     ⇒ 토큰을 **꺼내지 말고**, 브라우저 **안에서** API를 호출해 **응답만** 꺼낸다:
     ```
     ⑴ 로그인된 GG Club 탭에서 --print-snippet 의 헤더 가로채기를 쓰되, 헤더를 return 하지 않는다.
        같은 async 블록 안에서 그 헤더로 /api/gg-club/players/?page=N 전량 + /active-squad/ 를 부르고
        window.__ggPayload = JSON.stringify({players, squad}) 에 담는다. 헤더 변수는 null 로 버린다.
        ⚠️ SPA 이동은 **현재와 다른** /gg-club/my/… 링크를 눌러야 일어난다(같은 경로면 호출이 없다).
     ⑵ 화면에 COPY 버튼을 만들고(textarea + document.execCommand('copy'))
        computer{action:'left_click'} 로 **실제 클릭**한다 — 합성 이벤트·직접 호출은 false 를 뱉는다.
        ⛔ 브라우저 패널이 화면에 **표시**돼 있어야 클릭이 된다. 안 보이면 사용자에게 열어 달라고 한다.
        ⛔ Blob + a[download] 로 파일을 떨구는 우회는 **동작하지 않는다**(패널이 다운로드를 받지 않는다).
     ⑶ 셸에서  LANG=en_US.UTF-8 pbpaste > /tmp/ggclub-raw-YYYYMMDD.json
        ⚠️ LANG 없이 pbpaste 하면 한글이 깨져 UnicodeDecodeError 가 난다.
     ⑷ .venv/bin/python scripts/collect_ggclub.py --raw-file /tmp/ggclub-raw-YYYYMMDD.json --apply-squad
     ⑸ printf '' | pbcopy 로 클립보드를 비우고, 페이지의 COPY 버튼과 window.__ggPayload 를 지운다
     ```
     ⭐ 클립보드에 오르는 것은 **선수 데이터뿐이고 토큰이 아니다** — 「클립보드를 비우라」는 경고가 필요 없다(그래도 비운다).
     ⭐ 행 변환(29속성 파싱·6대 스탯)은 그대로 `collect_ggclub.py`가 한다 — **재구현하지 않는다**.
     ⚠️ `navigator.clipboard.writeText`는 브라우저 패널에서 **권한 정책으로 막힌다**(NotAllowedError) —
     반드시 `execCommand('copy')` 폴백을 쓴다.
   - ⚠️ `/api/gg-club/…`는 **Authorization 헤더 없으면 404**다(쿠키만으로는 안 된다). 토큰 수명은 **약 1시간**.

   - ⛔ 토큰은 **디스크에 쓰지 않는다**. 환경변수로 1회만 넘기고, 대화에 노출됐으면 사용자에게 알린다.

     브라우저 패널이 **https→http를 하드 차단**한다(`Access-Control-Allow-Private-Network`를 붙여도 `Failed to fetch`).

5. 페이지 순회·활성 스쿼드는 스크립트가 함께 처리한다(`?page=N` + `/api/gg-club/active-squad/`).

## ⛔⛔ 싱크 전에 **fut.gg가 최신인지** 먼저 본다 (2026-09-21 실증)

`fut_club_sync.py`는 `current_ovr`·`current_six`를 **무조건 덮는다**(충돌은 보고만 한다).
⇒ **fut.gg가 우리 원장보다 낡았으면 싱크가 진화를 되돌린다.**

- 실증(2026-09-21): 지모알로바 갈림길 1·2단계를 인게임에 적용하고 원장에 78로 기록한 직후 회차.
  fut.gg는 **EA 싱크 전이라 73**이었고, dry-run의 유일한 변경이 **「갱신 1 = 78→73 되돌리기」**였다.
- ⭐⭐ **2026-09-21부터 스크립트가 자동으로 막는다**(사용자 지시 「진화 선수들은 싱크 시 덮이지 않도록 별도 처리」):
  **진화 로그가 있는 선수는 EA 값이 원장보다 낮으면 `current_ovr`·`current_six`를 덮지 않고** 케미 스타일·개인 케미만 갱신한다.
  보고에 `🛡️ 진화 보호 N명`으로 뜬다. ⭐ **EA가 더 높으면 그대로 받는다** — 진화 완주가 fut.gg에 반영되는 경로는 막지 않는다.
  ⛔ 진화 기록이 틀렸다고 **확정**했을 때만 `--force-overwrite`로 덮는다.
- ⇒ 그래도 **`--dry-run`을 먼저 돌려** 「🛡️ 진화 보호」·「⚠️ 원장 ↔ EA 불일치」 줄을 읽는다.
  보호가 떴다면 fut.gg가 낡은 것이니 「Sync Club」으로 최신화한 뒤 다시 수집하는 편이 낫다(보호는 임시 방패일 뿐 정합을 만들지 않는다).
  ⭐ 진화를 여러 단계 밟을 계획이면 **마지막 단계까지 끝내고 한 번에** 싱크하는 편이 회차를 아낀다.
- ⚠️ 반대 방향(fut.gg가 최신, 원장이 낡음)이면 덮는 게 맞다 — 그때는 「진화 완주 추정」 보고를 보고 `fut_club.py complete`로 닫는다.

## 3. 원장 반영

1. 캡처 파일은 `collect_ggclub.py`가 `/tmp/ggclub-YYYYMMDD.json`에 이미 써 뒀다
   (`[{"ea","n","ovr","six":[6],"cs","cp","gg","added","paid"}, …]`).
2. `.venv/bin/python scripts/fut_club_sync.py /tmp/ggclub-YYYYMMDD.json --account main`
   - 신규는 추가, 기존은 OVR·6대 스탯·케미 스타일·개인 케미 갱신.
   - ⭐ **EA에 없는 보유 행은 「판 것」으로 보고 처분한다**(2026-09-20 사용자 지시 「판 선수는 확인 안 하고 없으면 업데이트하면 될 것 같고」).
     ⛔⛔ **단 예외가 하나 있다 — `fut_evolution_log`가 걸린 선수는 절대 자동 처분하지 않는다.**
     근거는 사용자 규칙이다: **「진화한 선수는 판매하지 않는다」.** 즉 진화 선수가 EA 목록에서 사라졌다면 그것은 매각이 아니라
     **다른 사정**(시장 등록·SBC 투입·일시적 누락)이고, 지우면 진화 이력까지 잃는다. ⇒ 그 경우만 **목록을 내고 사용자에게 확인**받는다.
     ⭐ 실증(2026-09-20): 맥긴이 EA 목록에서 빠졌는데 사용자가 「다시 스쿼드에 넣어둘 것」이라 해 보존했다 — 없다고 다 판 게 아니다.
   - ⭐ 「진화 완주로 보이는 선수」 보고가 뜨면 `fut_club.py complete`로 닫되, **어떤 진화였는지는 사용자에게 확인**한다
     (fut.gg는 경로를 주지 않는다 — 「GG Club tracks your players' final stats, but not the evolution path that created them.」).
     ⭐⭐ **단계 판정 순서**(2026-09-20 실증 · obs#900 → obs#904로 정정):
     ⑴ **기준 카드(`player_card_items`) ↔ 클럽 카드의 스탯 차이** ⑵ **카탈로그 단계별 보상과의 일치** ⑶ **EA 실측 PlayStyle**.
     ⛔⛔ **아이템 접미 `-N`을 단계 근거로 쓰지 말 것** — 넷째 보조 신호일 뿐이다. 반례: 지모알로바는 **2단계 완주인데 접미가 없었고**,
     그걸 보고 「아직 시작만 했다」로 잘못 적었다. 접미는 fut.gg가 변경을 감지한 뒤에 붙는 것으로 보인다.
     ⭐ 반면 ⑴⑵는 반례에서도 정확했다 — 기준 카드 65 ↔ 클럽 73 = 1단계 `Overall +8`, PlayStyle 핑드 패스 = 2단계 보상.
3. 활성 스쿼드 슬롯을 `fut_squad_slots`에 반영(11명 + 교체). 포메이션·감독 국적/리그가 바뀌었으면 `fut_squads`도 갱신.
   ⭐⭐ **`fut_tactics`·`fut_tactic_roles`는 어떤 스크립트도 갱신하지 않는다 — 매 회차 손으로 확인한다**
   (2026-09-22 실증: 싱크를 마쳤는데 화면의 「읽은 날」이 09-20에 멈춰 있었고, 실제로 **인게임 전술이 바뀌어 있었다**).

## 5. 종료 보고 (이 형식으로)

## ⭐⭐ 진화 적용 결과는 **EA 실측으로 더블체크**한다 (2026-09-20 실증)

⇒ **검증 절차**: GG Club API `playerDef.playstyles` / `playstylesPlus`는 **숫자 id**로 온다.
id→이름 표는 fut.gg 웹앱 번들에서 받는다(케미 스타일과 같은 경로) — `e[e.NAME=ID]=\`NAME\`` 열거형 + `[P.NAME]:\`Label\`` 라벨표를 짝지으면 된다.
확인된 값 일부: `6 핑드 패스 · 9 휘핑 패스 · 10 자키 · 11 블록 · 12 인터셉트 · 13 앤티시페이트 · 14 슬라이드 태클 · 17 래피드 · 19 퍼스트 터치 · 37 게임 체인저 · 38 인벤티브`.
⭐ **기준 카드(`player_card_items.playstyles`)와 대조하면 「어디까지가 진화분인가」가 갈린다** — 루제리는 기준 Whipped Pass + 진화 Jockey로 EA가 완전히 설명됐다.

## ⭐⭐ 진화 경로를 **추천**할 때 (2026-09-21 사용자 지시 「앞으로 진화 구현할 때 참고」)

원장 적재와 별개로 「어느 갈림길을 고를까」를 답할 때의 규칙이다.

1. **현재 카드 상태는 EA 실측으로 확정한다** — 기준 카드(`player_card_items.attrs`)에 적용된 진화 델타를
   **캡까지** 얹어 재구성하고, `fut_club_players.current_six`와 6개 전부 일치하는지 대조한다.
   ⭐ 2026-09-21 지모알로바에서 이 방법이 6/6 일치로 검증됐다. 불일치면 진화 단계 기록이 틀린 것이다.
2. **표기 상승분이 아니라 캡 반영 실제 상승분으로 비교한다.** 카탈로그의 「+7」이 캡에 걸려 **+0**이 되는 일이 흔하다
   (실증: 약발·스킬무브 +2★는 캡이 3★라 이미 3★인 카드엔 0 · 가속 +5는 캡 80인데 원값 84라 0).
3. **6대 스탯 기여로 환산한다** — `fc_face_stats`의 구성 가중을 쓴다(예: DRI에서 드리블 .45 > 볼컨 .30 > 민첩 .10).
4. ⭐⭐ **PlayStyle·Role+의 값어치는 근거 등급을 밝혀 판단한다**(불변규칙 12). 정본은 `game_system_changes`와 docs/22 §2.1.
   ⛔ 기각된 통설(반응력이 세컨볼을 결정한다 등)을 선택 근거로 쓰지 않는다.
   ⚠️ FC27 FUT에서 **스페셜 카드는 Role++를 일괄 보유**하므로 Role+를 주는 진화의 가치가 사라진다 —
   **베이스 카드에는 남는다.** 대상 카드가 어느 쪽인지 먼저 본다(`player_card_items.is_base`).
4-1. ⭐⭐ **갈림길(분기)은 `docs/22 §6.2`의 공통 기준으로 고른다** — ⑴ 이미 보유(이득 0) → ⑵ 역할 가중 → ⑶ 역할 적합.
   ⛔ **fut.gg가 고른 가지(★)를 그대로 따르지 않는다** — 기준이 공개돼 있지 않고, 실제로 낭비가 나온 적이 있다
   (알리송 2단계 First Touch = 이미 보유 → 이득 0). 화면이 ★와 우리 기준을 갈라 보여준다.
5. **이미 가진 축과 중복인지 본다** — 같은 일을 하는 레버가 이미 켜져 있으면 한계효용이 깎인다.
   ⚠️ 다만 First Touch PlayStyle이 볼컨트롤 원값을 얼마나 덮는지는 **정량 근거가 없다**(리서치 §3.3).
6. **순서 함정을 먼저 확인한다** — 요구조건(Max OVR · Max PS · Pace 상한)은 **시작 시점**에 검사되므로,
   OVR이나 PS를 올리는 진화를 먼저 하면 **무료 진화가 영구히 잠긴다**. 무료·저제한부터 배치한다.
7. **완주 결과는 표기값이 아니라 EA 싱크 실측으로 확정한다**(루제리 표기 83 ↔ 실측 80).

## ⭐⭐ 진화를 적용·완료했으면 **연관 메뉴를 한 번에 닫는다** (2026-09-22 사용자 지시)

진화 하나가 바뀌면 화면 여러 곳이 동시에 틀어진다. **로그 한 줄만 넣고 끝내면 나머지가 조용히 어긋난다.**
⇒ 아래를 **한 회차 안에서 전부** 확인한다. 건드릴 게 없으면 「변화 없음」이라고 적는다.

| # | 대상 | 무엇이 바뀌나 | 어떻게 |
|---|---|---|---|
| 1 | **`fut_evolution_log`** | 적용 사실 자체 | `fut_club.py evolve` · 다단계는 **단계마다 행**. 완주면 `--completed` |
| 2 | ⚠️ **`ovr_before`/`six_before`** | 스크립트가 **현재값을 before로** 넣는다 | **기준 카드 값으로 고쳐 쓴다**(실증: Adam Smith가 79→79로 들어갔다. 실제는 73→79) |
| 3 | **`fut_club_players`** | OVR·6대 스탯·PlayStyle·Role | 다음 GG Club 싱크가 채운다. ⚠️ **EA 싱크 전이면 fut.gg가 낡아** 진화 보호가 걸린다 |
| 4 | **진화 카탈로그 탭** | 1회성이면 **소진**돼 목록에서 빠진다 | 자동(`consumedMap`) — 로그가 있으면 따라온다. **소진 종수가 늘었는지 확인** |
| 5 | **선수별 진화 패스 탭** | 「이미 적용한 진화」 패널 · 경로의 `✓ 이미 적용 완료` | 자동(`appliedMap`) — **그 선수 패널에 실제로 떴는지 확인** |
| 6 | **전술 구현 · 구매 우선순위** | 그 진화를 쓰던 다른 선수의 추천이 **다시 매겨진다** | 자동. ⚠️ 1순위가 바뀌었으면 **종료 보고에 적는다**(사용자가 그걸 보고 산다) |
| 7 | **`site/data`** | 위 전부의 원천 | `export.py` → `db_dump.sh` → 명시 스테이징 커밋 |

⛔ **로그를 넣었는데 화면이 안 바뀌면 그게 버그다** — 「반영됐겠지」로 넘기지 말고 그 자리에서 확인한다.
   실증(2026-09-22): 소진 진화가 카탈로그 탭에는 그대로 남아 있었다(`pathOpen`이 다른 탭만 걸렀다).
⛔ **DB 행을 지워서 목록에서 빼지 않는다.** 로그를 남기면 화면이 알아서 감춘다 —
   `fc_evolutions` 행을 지우면 `fut_evolution_log.evo_id`가 가리킬 곳을 잃어 **무슨 진화를 밟았는지**가 사라진다.
⭐ **어떤 진화였는지 모르면 사용자에게 묻는다**(fut.gg는 경로를 주지 않는다).
   단 **스탯 대조로 좁힐 수 있다** — 기준 카드 ↔ 현재의 6대 스탯이 카탈로그 상한과 몇 개나 맞는지 보면 거의 확정된다
   (실증: Adam Smith는 6/6 일치로 「Intro to Evolutions」가 확정됐다). §3-2 단계 판정 순서 ⑴⑵와 같은 방법이다.

## ⭐ 진화 소진 규칙 (2026-09-20 사용자 지시)

**한 계정에서 쓴 진화는 다른 선수가 쓸 수 없다.** 반복형은 `repeatability` 횟수만큼만 쓸 수 있고, 그 횟수를 채우면 **소진**이다.
⇒ 소진된 진화는 **카탈로그·선수별 경로·전술 구현 탭 전부에서 빠지고** 각 선수의 최적 패스가 다시 매겨진다(`site/evolutions.html` `consumedMap`).

⛔⛔ **세는 단위는 「적용 횟수(run)」이지 로그 행 수가 아니다** — 2026-09-20에 이 둘을 혼동한 버그를 고쳤다:
- **1단계 행(`level=1`)만 센다.** 반복 배급은 4단계짜리라 한 번 밟아도 행이 4개 쌓인다 — 그대로 세면 1회가 4회가 되어 `repeatability=2`짜리가 첫 선수만으로 잠겼다.
- **`is_void=1` 행은 세지 않는다**(migration 053). 마조 Striker Glow Up은 실측으로 「적용된 적 없음」이 확인됐는데도 소진으로 잠겨 있었다.
- ⭐ **진행 중(`completed_at IS NULL`)도 센다** — 카드가 이미 그 경로에 묶였기 때문이다.
